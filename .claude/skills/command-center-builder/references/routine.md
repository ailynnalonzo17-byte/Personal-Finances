# The Morning Routine — regenerating `personal.json`

## ⛔ READ FIRST — this IS a scheduled cloud routine (settled by Stephanie 09-08-2026)

**This file has flip-flopped and this is the final position. The briefing is a scheduled Claude
cloud routine with the student's connectors and repo attached.** An earlier banner here said a
cloud agent "cannot reach their connectors" and moved the briefing into a Daily Routines row.
That reason was false: a cloud routine with connectors attached reads Calendar, Slack, Gmail and
Airtable, and pushes to the attached repo, proven on Stephanie's own build five mornings running.

Why the cloud, in her words: "if these are all connectors, wouldn't we want it run in the cloud?
If we taught only in routines, they'd lose the currentness of the data." Exactly. A Daily Routines
row runs only when the student opens Claude on their machine; the cloud routine fires at 5am with
the laptop closed. Every day-one source is a connector, so nothing is lost by running in the cloud.

Two things that remain true and matter:
1. **A cloud routine cannot see anything local**: a self-hosted mail server, a local MCP server,
   files outside the attached repo. That is the ONE case for a Daily Routines row instead, and a
   connector-only student does not have it.
2. **A cloud routine can report SUCCEEDED while doing nothing.** Watch for the commit, read the
   first run log. Never trust the flag.

**So `personal.json` is regenerated by the cloud routine each morning.** Vera creates it with the
`schedule` skill / RemoteTrigger at the end of the build, attaches every connector the student
already has, attaches their repo, and runs it once on the spot.

The `data.json` half is separate: a plain GitHub Action running `bake.mjs` with API tokens as
build secrets, no connectors involved, on its own 2-hourly schedule.

The written briefing (mindset, leverage action) and every company's
Calendar/Slack/Email/Power Move need an **agent** — an LLM that reads the student's context and
connectors — so they cannot come from the build script. They come from the cloud routine, writing
`command-center/public/personal.json` and pushing to main; Cloudflare redeploys.

## Create it — automatically, as the last step of the build

Vera does this without being asked AND without asking permission, the moment Phases 1 to 4 are
done (Stephanie, 09-08-2026: "can you create the morning briefing automatically after the command
center is built?" Yes. And 09-09-2026: "it looked like she asked for permission to push and merge
and also permission to create the routine. Don't have her ask, that's confusing.") Narrate each
step in one line; do not pause for a yes.

1. **Create the cloud routine** with the `schedule` skill (RemoteTrigger `create`): name
   "Command Center — morning briefing", cron for 5am in the student's timezone (cron is UTC; note
   the DST hour), model `claude-opus-5`, `sources` = their GitHub repo, `mcp_connections` = every
   connector they have already connected (Calendar, Slack, Gmail, Airtable, QuickBooks as
   applicable). The connector UUIDs come from their claude.ai connectors; reuse them from any
   existing routine of theirs if this session cannot list them.
2. **The routine's prompt is `assets/routine-prompt.md`**, filled in for them.
3. **Run it once NOW** (`RemoteTrigger run`, then watch for the commit as described under Test
   it). Cloudflare redeploys on the push. Open the page. Their real HQ and company content is on
   screen within minutes of the build ending. **This is why there is no hand-seeded briefing any
   more** — the real one arrives before they have finished their coffee.
4. **Say when it runs next**: tomorrow at 5am, laptop open or closed. Relay the routine's
   claude.ai link so they know where to look if a morning ever fails.

**A connector they add later** (a padlocked tool they connect next week) must ALSO be attached to
the routine's `mcp_connections`, or the routine still cannot see it. That is a Vera step, one
line, in the session where they tell you they connected it.

**Push access — VERIFIED 09-04-2026 on the reference build.** The cloud routine has the repo
attached as a source and pushes to `main` on its own, and **Cloudflare rebuilds and redeploys on
the push itself**, within seconds. Proven three ways in one sitting:
a deliberate marker commit pushed at 20:58:38Z appeared in Cloudflare's build history "a few
seconds" later and was live on the site before the next scheduled run; and two earlier
*Claude-authored* briefing commits that day (`46849a3`, `ad24b61`) each show in the same build
history as their own successful build.

**Know which mechanism does what**, or you will misread a failure:
- **Cloudflare Workers Builds** watches the repo and fires on every push to the watched path.
  This is what publishes `personal.json` the moment the morning pass commits it.
- **The GitHub Action** (`refresh-command-center.yml`) has **no `push` trigger** — only the
  2-hourly cron and manual dispatch. It exists to re-bake `data.json` from the database on a
  schedule and deploy the result. It is not what publishes a briefing.

Still confirm the commit landed and the site updated the first time you set this up for a
student — their watch path may be narrowed differently.

## The prompt (full template in `assets/routine-prompt.md`)
Its structure, and why each part is there:
1. **Unattended framing** — "do not ask questions; use connectors, secrets, and the repo,
   then commit." Cloud runs can't wait for a human.
2. **Read `sources.json` first** — the map is the authority for what to pull and how.
3. **Ground in CURRENT focus** — read the student's own "programs/offers/priorities"
   note as the source of truth and weight by it. This is the fix for the #1 content bug
   we hit: a prompt that hard-codes priorities goes stale (the reference prompt inherited
   an old spec that led with a dormant course instead of the active launch). Name the
   active launch, tell it not to over-index on older priorities, and let the vault decide.
4. **Per company:** Calendar (one shared calendar, LLM-classified with hints); Slack
   (connector or per-workspace token — `printenv` for the secret; if missing, emit the
   🔒 pending object); Email (multi-Gmail server via HTTP if its secrets exist; dedicated
   inboxes + wildcard by label + LLM fallback; else 🔒); Power Move (3–5 bullets, ONE
   revenue/priority action, never re-contact someone already contacted per outreach
   context); pulse; and for non-database companies a headline + status + items.
5. **HQ:** mindset (real neuroscience quote + note), leverage (full phrases "High Leverage /
   Long-Term Payoff" / "Low Leverage / Short-Term Payoff" — never "Q4/Q1"; no closing
   question, the page renders it). There is no worth anchor (removed 09-08-2026).
6. **Exact output JSON shape** — spell it out; the page's renderers depend on the keys.
7. **Publish:** write the file, `git add/commit/push origin main`, report push errors,
   one-line summary.
Tone constraints that matter to this student (direct accountability, no motivational
language, no affirmations, sharp chief-of-staff power moves) are in the template — keep
them; they're what made the output feel true instead of generic.

## Secrets the routine needs (student adds in the routine's settings on claude.ai)
| Secret | Enables |
|---|---|
| `SLACK_TOKEN_<WORKSPACE>` (one per API-reached workspace) | that company's Slack panel |
| multi-Gmail server URL + bearer token (e.g. `MULTI_GMAIL_URL`, `MULTI_GMAIL_TOKEN`) | all Email panels |
| (the database token is *not* needed here — the baker handles `data.json`) | |
Connectors (Calendar, the connected Slack workspace, Airtable) need no secrets. Anything
missing renders 🔒 with the exact secret name, so the student can add them one at a time.

## Test it — always, before trusting the schedule
1. `RemoteTrigger run` → returns a `session_id`.
2. Watch for the commit rather than polling the log (the log is huge): a background
   loop on `gh api repos/<owner>/<repo>/commits?path=command-center/public/personal.json`
   until the newest message matches the routine's commit message. (Foreground `sleep` is
   blocked in Claude Code — use a background `until` loop.)
3. Read the result: fetch `personal.json` from GitHub and print, per company, whether
   calendar/slack/mail/powerMove came back live, empty, or 🔒 pending. Show the student.
4. If something's wrong, `RemoteTrigger get_run_log <session_id>` shows every tool call
   and error. Common first-run findings: a stale-priority framing (fix the prompt), a
   source the routine reached via the connector that you expected to be pending (fine),
   Email 🔒 (expected until the multi-Gmail secrets exist).
Note: there is no hand-seeded `personal.json` any more; the first real run at the end of the
build is what the student sees first.

## Retire the old
If the student had a previous "daily briefing" automation (a Slack Canvas post, an old
routine), **disable it rather than delete it** (`RemoteTrigger update {enabled:false}`)
until they've lived with the new tab and decided. On the reference build a prior cloud
routine had been reporting SUCCEEDED for weeks while doing nothing (the cloud env lacked
the artifact tools it needed) — success flags are not evidence of work; read run logs.
